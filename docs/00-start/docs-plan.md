## 1. Цель и стандарт качества

Документация «Партнера» — часть продукта: покупатель ставит систему в свой
репозиторий и читает только ее. Цель плана — довести все 21 существующий
документ и новые пакеты D4–D9 до состояния, когда сторонняя организация
успешно внедряет и эксплуатирует систему без участия автора.

Стандарт качества (проверяется на каждом документе):

1. Шапка-таблица: версия, дата, назначение, связанные документы.
2. Одна аудитория на документ (см. §2); терминология — только по глоссарию.
3. Каждая цифра примера воспроизводима: числа T-сценариев совпадают с
   `tests/test_calc.py`, дефолты политики — с `policy.example.yaml`.
4. Перекрестные ссылки не ведут в пустоту (проверка валидатором ссылок).
5. Статус жизненного цикла проставлен в реестре (§7): draft / review /
   approved. Публиковать можно только `approved`.

## 2. Аудитории и их маршруты чтения

| Аудитория | Маршрут | Что должна уметь сделать |
|---|---|---|
| Директор (покупатель) | quickstart → vision → digest-and-cli | пройти `partner init`, читать дайджест дня/месяца |
| Юрист | equity-model → legal-module → пакет юристу | понять фантомные доли, подписать документы |
| Разработчик клиента | repo-pack → time-accounting → connectors | подключить агента к учету, чинить ошибки |
| Админ (у клиента) | installation → threat-model → runbook | поднять Docker Compose, настроить бэкапы |
| Разработчик продукта | development-plan → data-model → calculator-spec | вести I4–I9 без вопросов к автору |

Правило: документ пишется для одной аудитории; если нужен второй —
внутри ставится короткий «перевод» со ссылкой на профильный документ.

## 3. Жизненный цикл документа

```
draft → self-check (§1) → review вторым читателем → approved → публикация
          ↑__________________ правки возвратом в draft __________________↑
```

- Правка в `approved`-документ возвращает его в `review`; в реестре меняется
  версия.
- Изменение цифр расчета (ставки, капы, коэффициенты) идет в одном PR вместе
  с изменением golden-тестов и соответствующего раздела документа —
  «документация и код меняются вместе».

и код, который она описывает.

## 7. Правила изменения плана

- Новая итерация или изменение DoD — коммит `docs(plan): …` со ссылкой на
  issue; если затронуты правила расчета — со ссылкой на ADR.
- Документ уходит в `approved` только после прохождения self-check §1.
- Расхождение числа в документе и теста — баг documentation-трека,
  исправляется в том же PR, что и тест.
