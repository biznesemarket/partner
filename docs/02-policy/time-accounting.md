# Модель учета времени с ИИ-агентом

| Поле | Значение |
|---|---|
| Код | POLICY-TIME |
| Версия | 0.1 |
| Дата | 2026-11-13 |
| Статус | Действует как норматив расчета |
| Связанные | ADR-0016, ADR-0017, equity-model, calculator-spec, tests/test_calc.py |

## 1. Назначение

Определить, какое время считается рабочим, как оно оплачивается
и как превращается в долю. Документ нормативный: два независимых
читателя обязаны получить одинаковый результат по сценариям §13.
Сценарии закреплены автоматическими тестами в `tests/test_calc.py`.

## 2. Событие активности (heartbeat)

Агент-кит отправляет событие каждые `heartbeat_interval_sec` (дефолт 30):

| Поле | Описание |
|---|---|
| event_id | UUID, идемпотентность |
| session_id | сессия работы |
| participant_id | человек-владелец |
| project_id | проект |
| ts_client_utc | время клиента (справочно) |
| agent | attached, agent_id, model, running |
| signals | input_events, focus, scroll, tool_calls, files_touched, commits |
| seq | монотонный номер устройства |
| device_id, signature | подпись батча |

Серверное время `received_at` — авторитетное. Расхождение часов клиента
больше `max_clock_skew_sec` (дефолт 300) → событие помечается флагом.

Сессия обязана иметь привязку к задаче/ветке. Без привязки — учитывается,
но не оплачивается, флаг `no_task_link`.

## 3. Классы времени

| Класс | Условие | Коэффициент |
|---|---|---|
| `active_human` | есть ввод/навигация за последние `active_window_sec` (120) | 1,0 |
| `supervised_agent` | ввода нет, но окно в фокусе и присутствие подтверждено за `presence_window_sec` (600), агент работает | `k_supervised` (дефолт 1,0) |
| `autonomous_agent` | агент работает, присутствия человека нет | `k_autonomous` (задаёт директор, реком. 0,2–0,3) |
| `idle` | нет активности человека и агента дольше `idle_timeout_sec` (300) | 0 |

Присутствие человека = любой сигнал (клавиатура, мышь/скролл, смена файла,
фокус, ответ агенту) в окне присутствия. Чтение вывода агента со скроллом
считается присутствием.

Классификация выполняется для каждого интервала между событиями.

## 4. Формулы и порядок применения

Порядок строго детерминирован:

1. Классифицировать интервалы
2. Объединить пересекающиеся интервалы человека (union), не суммировать
3. Разрезать интервалы по границе суток и по смене версии ставки
4. `paid_hours = (active + supervised×k_sup + autonomous×k_auto) / 3600`
5. Применить кап автономного класса: `autonomous_paid ≤ autonomous_paid_cap_hours`
6. Применить дневной кап: `total_paid ≤ daily_cap_hours`.
   Приоритет усечения: сначала сохраняется `active_human`,
   затем `supervised_agent`, затем `autonomous_agent`
7. `amount_rub = ROUND_HALF_UP(paid_hours × rate_rub_per_hour × k_quality, 2)`
8. `share_pct = amount_rub / valuation_rub × 100`

Все вычисления — в целых копейках и секундах; никаких float.
`k_quality` — опциональный коэффициент дня (дефолт 1,0), задается
директором с обоснованием; без него не применяется.

## 5. Ограничения

| Ограничение | Переменная | Дефолт |
|---|---|---|
| Дневной кап оплачиваемых часов | `daily_cap_hours` | 12 (спрашивается при настройке) |
| Кап автономного класса (оплач. ч) | `autonomous_paid_cap_hours` | 2,0 |
| Параллельные сессии человека | union в рамках организации | всегда |
| Простой | `idle_timeout_sec` | 300 |
| Сессия без задачи | не оплачивается | всегда |
| Работа без агента | `manual_only_policy: track_only` | track_only |

Параллельные сессии одного человека в разных проектах объединяются:
интервал относится к проекту с наибольшим числом сигналов; при равенстве —
к проекту, где сессия началась раньше. Двойной оплаты не бывает.

## 6. Закрытие дня

- Граница суток: 00:00 настроенного пояса, дефолт `Europe/Moscow` (UTC+3).
- События хранятся в UTC; сессии через полночь разрезаются.
- В 00:00 планировщик: закрывает день, применяет формулы, пишет дневную
  запись, блокирует события дня от изменений, ставит флаги.
- Утром в `digest_hour` (дефолт 09:00) отправляется дайджест.
- Подтверждение директора не требуется (ADR-0017).

## 7. Опоздавшие события и offline

Агент-кит буферизует события локально, подписывает и отправляет при связи.
Сервер принимает опоздавшие события в течение `late_grace_hours` (дефолт 24).
Если день уже закрыт — пересчет создает **компенсирующую запись**, исходная
не изменяется. Позже грейса — событие помечается `late_rejected`
и учитывается только по решению директора.

Реализация v1.2 (ADR-0021): `service.close_day` не перезаписывает принятый
`day_record`; повтор с теми же числами идемпотентен, а изменившийся пересчет
создает `adjustment` на дельту от эффективной суммы с детерминированным id
(повтор не дублирует компенсацию). Часы закрытой записи сохраняются,
пересчитанные часы и разница видны в дайджесте и аудите.

## 8. Версии ставки и оценки

Ставка и оценка — версионируемые переменные политики (см. versioning.md).
Новая версия действует с указанного момента. Интервалы до и после смены
ставки считаются по своим ставкам. Прошлые начисления не пересчитываются.
Накопленные рубли неизменны; отображаемая доля считается от текущей оценки
(переоценка размывает всех прозрачно и объявляется заранее).

## 9. Антифрод: флаги дня

| Флаг | Условие |
|---|---|
| `no_output` | > 3 оплачиваемых часов при нулевых коммитах, диффах и вызовах инструментов |
| `synthetic_input` | интервалы ввода без вариативности (эвристика) |
| `night_autonomous_spike` | автономный класс > 6 ч за ночь |
| `clock_skew` | расхождение часов клиента сверх порога |
| `replay` | повтор event_id или нарушение seq |
| `no_task_link` | сессия без привязки к задаче/ветке |
| `cap_applied` | применен дневной или автономный кап |

Флаг не отменяет начисление автоматически (кроме `replay`), но помечает
день для директора и попадает в дайджест.

Реализация v1.1: `no_output` ставится сервером (`service._no_output_flag`),
если оплачено > 3 ч и равны нулю сумма `signals.tool_calls`, коммиты и
PR-диффы, привязанные к ветке/задаче сессий участника (`repo_facts`).
Флаг не меняет формулу и снимается только новым расчетом дня.

## 10. Корректировки и споры

Окно `day_dispute_window_days` (дефолт 3 суток с закрытия дня).
Директор корректирует день компенсирующей записью с обоснованием.
Разработчик оспаривает через форму спора; ответ — до 2 рабочих дней.
Месячный снапшот имеет свое окно (7 дней) и не переписывает дни молча.

## 11. Доказательства и хранение

| Данные | Хранение |
|---|---|
| Сырые события | PostgreSQL, `raw_events_retention_days` (90) |
| Интервалы и классы | PostgreSQL, бессрочно |
| Дневные записи | PostgreSQL + якорь в git (append-only) |
| Месячный снапшот | git, с SHA-256 входных данных |

Любая цифра дайджеста раскладывается командой `partner explain <date>`:
интервалы, классы, коэффициенты, капы, ставка, флаги.

## 12. CLI и дайджест

```text
partner status                 # текущая сессия и день
partner day [YYYY-MM-DD]       # итог дня
partner explain YYYY-MM-DD     # раскладка расчета
partner snapshot YYYY-MM       # месячный снапшот
```

Дайджест содержит: оплачиваемые часы по классам, рубли и % за день,
накопленные рубли и %, применённые капы, флаги, ближайшую веху.

## 13. Приемочные сценарии

Ставка 500 ₽/ч, оценка 10 000 000 ₽, кап 12 ч, k_sup 1,0, k_auto 0,2,
кап автономного 2,0 оплач. ч.

| # | Вход | Ожидаемый результат |
|---|---|---|
| T-01 | active 4 ч, supervised 2 ч, autonomous 3 ч, idle 1 ч | paid 6,6 ч → 3 300 ₽ → 0,0330% |
| T-02 | ночь: только autonomous 8 ч | paid 1,6 ч (≤ кап 2,0) → 800 ₽ |
| T-03 | active 10 ч + supervised 4 ч | paid 14 → кап 12 ч → 6 000 ₽, флаг cap_applied |
| T-04 | сессии 10–12 и 11–13 | union 3 ч, не 4 ч |
| T-05 | сессия 22:00–02:00 | день D: 2 ч; день D+1: 2 ч |
| T-06 | ставка 500 до 14:00, 600 после; active 09–15 | 5×500 + 1×600 = 3 100 ₽ |
| T-07 | простой 20 мин без сигналов | 0 ₽ за интервал, сессия на паузе |
| T-08 | offline 3 ч, загрузка через 5 ч | учтено (в грейсе), компенсирующая запись |
| T-09 | offline 30 ч, загрузка позже грейса | late_rejected, 0 ₽ до решения директора |
| T-10 | работа без агента 4 ч | track_only: учтено, 0 ₽ |
| T-11 | T-01 + k_quality 1,1 | 3 630 ₽ |
| T-12 | autonomous 12 ч | paid 2,4 → кап автономного 2,0 ч → 1 000 ₽ |

## 14. Что не делаем

Не считаем строки кода и коммиты как оплату. Не оплачиваем присутствие
без сигналов. Не начисляем задним числом по новым правилам. Не храним
содержимое файлов и переписку — только метаданные активности.
