# ADR-0020: Политика резервного копирования и репетиция восстановления

| Поле | Значение |
|---|---|
| Статус | Принято |
| Дата | 2026-11-13 |
| Решающий | Основатель |
| Заменяет | ADR-0013 (две копии бэкапа на площадке) |

## Контекст

ADR-0013 разрешал две копии бэкапа на площадке, пока нет внешних
участников. После M4 (сервер — единственное хранилище расчетов:
day_records неизменны и стоят денег) потеря БД = потеря начислений и
долей. Снапшоты долей (M7) и git-якоря восстанавливают лишь месячные
итоги, не дневную детализацию. Задача I8 требовала пересмотра.

## Решение

1. **Ежедневный автоматический дамп** PostgreSQL (pg_dump -Fc, сжатие) —
   сервис `backup` в Docker Compose, раз в сутки в `PARTNER_BACKUP_AT`
   (по умолчанию 02:00 пояса хоста).
2. **Проверка каждого дампа сразу после снятия**: `gzip -t` +
   `pg_restore --list`. Битый дамп удаляется и не считается бэкапом.
3. **Хранение N дней** (`PARTNER_BACKUP_KEEP_DAYS`, дефолт 14) + правило
   двух площадок: как минимум одна копия дампов выносится за пределы
   сервера (офсайт: git-LFS-зеркало, S3-совместимое хранилище или
   скачивание администратором — способ фиксирует клиент в installation.md).
4. **Репетиция восстановления** — `restore_check.sh`: восстановление
   последнего дампа во временную БД и сверка с боевой (версия схемы,
   число таблиц, количество и сумма day_records, sha256). Запуск — после
   установки, далее ежеквартально и при каждом обновлении (входит в
   upgrade.sh перед миграцией).
5. **Бэкап перед каждой миграцией** — шаг 2 в upgrade.sh (M8.2):
   обновление схемы без свежего дампа запрещено.

## Альтернативы

WAL-архив / point-in-time recovery — отложено до появления требования
«непрерывность к 00:00 закрытия дня»: потери последнего дня приемлемы
(дни закрываются по openable-интервалам заново, heartbeats — входные
данные агентов хранятся у клиента отдельно). Сторонний сервис бэкапов —
отклонено для self-hosted (данные клиента не покидают контур без его
решения — vision «данные клиента — у клиента»).

## Последствия

Плюсы: восстановление проверено до инцидента, а не во время него;
RPO ≤ 24 ч, RTO ≤ 30 мин (по регламенту runbook §потеря данных).
Минусы: 2× место под дампы (working + офсайт); pg_dump при больших
объемах — при росте объема данных вернуться к инкрементным копиям.
