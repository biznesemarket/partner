## 1. Утро: сводка проекта

Начните с текущего месяца: `GET /v1/status/summary`.

```bash
curl -sS "https://partner.example/v1/status/summary?project_id=partner" \
  -H "Authorization: Bearer $PARTNER_DIRECTOR_TOKEN"
```

```json
{
  "month": "2026-11",
  "participants": [
    {"participant_id": "p-01", "paid_hours_month": "5.0", "amount_rub_month": "2500"},
    {"participant_id": "p-02", "paid_hours_month": "5.8", "amount_rub_month": "2900"},
    {"participant_id": "p-03", "paid_hours_month": "4.0", "amount_rub_month": "2000"}
  ]
}
```

Итого за месяц-пример: 14,8 оплач. ч и 7 400 ₽. Проверьте, что версии
ставки и оценки — ожидаемые (`r1`, `v1` в дайджесте дня); изменение
ставки действует только с даты, задним числом не применяется.

## 2. Флаги: что требует внимания

Сводка не показывает флаги; они видны в дневном дайджесте участника.
Запросите дайджест за закрытый день:

```bash
curl -sS "https://partner.example/v1/digest/day/2026-11-12?participant_id=p-02&project_id=partner" \
  -H "Authorization: Bearer $PARTNER_DIRECTOR_TOKEN"
```

```text
Дайджест дня 2026-11-12 — p-02 (проект partner, Europe/Moscow)
Оплачиваемое время: 5.8 ч
  человек (active_human): 5.8 ч
  агент под наблюдением (supervised_agent): 0 ч
  автономный агент (autonomous_agent): 0 ч
Начислено: 2900 ₽ (cash 0 ₽ / доли 2900 ₽)
Доля дня: 0.0290 % (2.9000 бп)
Флаги: no_output
Версии: ставка r1, политика v1; sha256 7b2e…
```

| Флаг | Что значит | Действие директора |
|---|---|---|
| `no_output` | > 3 оплач. ч без коммитов/PR с диффами и без `tool_calls` | проверить задачу; при необходимости открыть спор |
| `idle_no_signal` | супервизия без сигналов ввода | уточнить у участника; класс мог стать `idle` |
| `synthetic_input` | серия одинаковых интервалов — макросы/автокликеры | запросить объяснение, проверить ветку |
| `night_autonomous_spike` | автономная работа ночью > 6 ч | проверить, что агент не оставлен на ночь без задачи |
| `clock_skew` | часы источника ушли вперед | проверить устройство/часовой пояс |
| `late_rejected` | событие пришло позже грейса и не оплачено | сообщить участнику; оплата только через спор |

Антифрод-флаги не меняют начисление автоматически; на оплату влияют
только правила классов (включая `idle`), капы и отклонение
`late_rejected`. Решение о деньгах принимает директор.

## 3. Спор дня

Участник открывает спор по закрытому дню в окне 3 суток
(`PARTNER_DISPUTE_DAYS`); один открытый спор на день. Список открытых:

```bash
curl -sS "https://partner.example/v1/disputes?status=open&project_id=partner" \
  -H "Authorization: Bearer $PARTNER_DIRECTOR_TOKEN"
```

Решение — `approved` с денежной дельтой или `rejected`:

```bash
curl -sS -X POST "https://partner.example/v1/disputes/dsp-4f2a9c1b7e30/resolve" \
  -H "Authorization: Bearer $PARTNER_DIRECTOR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"decided_by":"director","decision":"approved","delta_cents":-50000,
       "resolution":"интервал 14:00–15:00 был простоем"}'
```

Что происходит:

1. `approved` создает append-only `adjustment` на −500 ₽; исходный
   `day_record` не меняется (ADR-0021).
2. Эффективная сумма дня: 2 900 − 500 = **2 400 ₽**. В дайджесте
   появится строка `Корректировки: -500.00 ₽ → итог 2400 ₽`.
3. Доля дня в закрытой записи остается 0,0290%: корректировка меняет
   денежную сумму, а не пересчитывает исторический расчет. Пересчет
   начисления задним числом запрещен.
4. После дедлайна спор получает `expired`, решение невозможно.
5. Решение и корректировка попадают в аудит и очередь уведомлений.

Проверить эффективную сумму и раскладку можно через
`GET /v1/days/{date}?participant_id=…` и
`GET /v1/days/{date}/explain?participant_id=…`.

## 4. Поздние события

- Событие в пределах грейса сервера (`PARTNER_GRACE_HOURS`, по умолчанию
  24 ч) принимается; при повторном закрытии дня разница оформляется
  компенсирующей корректировкой.
- Событие за грейсом отклоняется (`late_rejected`) и не оплачивается.
- Повторная компенсация идемпотентна: тот же пересчет не создает вторую
  корректировку.
- Если пересчет и корректировка расходятся, дайджест вернет
  `day_mismatch` — это сигнал проверить целостность БД, а не «чинить»
  цифры вручную.

## 5. Закрытие месяца

### 5.1 Проверки перед снапшотом

1. Все дни месяца закрыты. Месячный дайджест показывает pending:
   `GET /v1/digest/month/2026-11?participant_id=p-01&project_id=partner`
   (повторить для каждого участника).
2. Открытых споров нет: `GET /v1/disputes?status=open&project_id=partner`.
3. Флаги просмотрены; решения по спорным дням зафиксированы.
4. Версии ставки и оценки соответствуют решениям; задним числом ничего
   не менялось.
5. Лицензия в состоянии `active` или `grace` (`GET /v1/license`);
   `invalid/expired` блокирует закрытие дня (402), но не чтение данных.

### 5.2 Снапшот

```bash
curl -sS -X POST "https://partner.example/v1/snapshots/2026-11?project_id=partner" \
  -H "Authorization: Bearer $PARTNER_DIRECTOR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"actor":"director"}'
```

Ответ содержит `snapshot_id`, `sha256`, `git_ref` и число участников.
Снапшот иммутабелен:

- повтор с тем же содержимым → `duplicate`;
- изменившиеся числа за тот же месяц → `snapshot_conflict` (422):
  сначала разберитесь с корректировками, затем фиксируйте новый месяц.

Для одного проекта удобен CLI:

```bash
export PARTNER_SERVER_URL=https://partner.example
export PARTNER_API_TOKEN=...
partner snapshot-close 2026-11 --by director
```

### 5.3 Юридический модуль

Модуль по умолчанию выключен, учет и снапшоты работают без него.
Включение — только после снятия гейтов G-01…G-08 юристом:

```bash
partner legal-gates
partner legal-enable --by lawyer
partner export-legal --to lawyer/ --by director
```

Пакет юристу содержит политику, снапшоты, гейты, вопросы и шаблоны; в
нем нет персональных данных. Подписывается `MANIFEST.txt` и листы
снапшотов.
