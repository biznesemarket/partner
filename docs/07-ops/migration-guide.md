# Migration guide: переход на v1.0.0

| Поле | Значение |
|---|---|
| Версия | 1.0 |
| Дата | 2026-11-13 |
| Аудитория | администратор клиента |
| Связанные | installation.md, runbook.md, CHANGELOG.md |

## 1. С какого уровня вы обновляетесь

| Исходная версия | Путь |
|---|---|
| CLI-прототип 0.1–0.3 (SQLite, без сервера) | §2 — перенос в серверный контур |
| Сервер 0.4–0.7 (M4–M7) | §3 — миграции + новые env |
| Сервер 0.8 (M8) | §4 — только лицензирование и devices |

Правило неизменно: **backup → alembic upgrade → перезапуск** (M8.2,
`deploy/scripts/upgrade.sh`); закрытые дни между версиями не пересчитываются
(V-02/V-04).

## 2. С CLI-прототипа (SQLite) на сервер v1.0.0

1. Поставить серверный контур по installation.md §2 (Docker Compose).
2. Зафиксировать политику: `partner policy set …` → экспортировать
   `policy.yaml` → загрузить на сервер `POST /v1/policies` (новая версия,
   `effective_from` — дата установки; заднее число запрещено V-02).
3. Исторические дни прототипа НЕ переносятся сервером автоматически:
   либо остаются в SQLite-архиве (режим демо сохранен, `partner day`),
   либо переносятся разово через `POST /v1/heartbeats` из экспорта
   прототипа — после переноса закрыть дни (`docker compose run --rm dayclose`).
4. Сверка: `GET /v1/status/summary` против `partner status` прототипа —
   расхождение по закрытым дням = ошибка переноса, откат: backup §5.

## 3. С сервера 0.4–0.7 на 1.0.0

1. `deploy/scripts/upgrade.sh 1.0.0` — скрипт сам сделает бэкап, накатит
   миграции 0004_m8 (day_records.closed_at) и 0005_m9 (таблица devices).
2. Добавить в deploy/.env новые переменные (см. installation.md §2):

   ```
   PARTNER_LICENSE_KEY=…        # выдан при оформлении подписки (M9.1)
   PARTNER_LICENSE_SECRET=…     # секрет поставки (вне канала ключа)
   PARTNER_LICENSE_REQUIRED=1   # боевой контур
   PARTNER_LICENSE_GRACE_DAYS=14
   # опционально, threat-model §4:
   PARTNER_REQUIRE_DEVICE_SIGN=0
   ```

3. Проверка: `curl /v1/license` → `"state":"active"`; закрытие дня —
   `docker compose run --rm dayclose`.

## 4. С сервера 0.8 на 1.0.0

Только шаг 2 из §3 (env лицензии); миграций схемы нет — 0004/0005 уже
накатаны. Регистрация устройств источников (при включении
`PARTNER_REQUIRE_DEVICE_SIGN=1`): `POST /v1/devices` на каждого агента,
секрет — в конфиг agent-kit, старые устройства отзывать после ротации.

## 5. Откат

`deploy/scripts/rollback.sh <предыдущий тег>`; откат схемы из миграций
0004/0005 не требуется (только добавление). Восстановление БД — только
из дампа и по явному решению (runbook §5.2).
