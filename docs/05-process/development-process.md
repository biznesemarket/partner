## 1. Git-workflow

- Модель: trunk-based + ветки задач `dev/<логин>/<тема>`.
- Коммиты: Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`).
- main защищен: только через PR, CI обязателен. Пока сопровождающий один —
  0 approvals (временное исключение); при втором ревьюере — ревьюер ≠ автор
  и 1 approval.
- PR связывается с задачей (issue); в PR — отметка об использовании агента.

## 2. Ревью и приемка

| Правило | Значение |
|---|---|
| SLA ревью | первый ответ — 1 рабочий день |
| Чеклист ревьюера | тесты проходят, документация согласована, нет секретов, маркировка агента |
| Самоприемка | фиктивное ревью через вторую учетку запрещено; при одном сопровождающем действует исключение 0 approvals |
| Golden-тесты | изменение цифр T-сценариев и документации — только в одном PR |

## 3. Политика AI-агентов (кратко; полный текст — AGENTS.md)

- Ответственность за результат несет человек-владелец сессии.
- Коммиты агента маркируются `Co-authored-by: <agent> <agent@…>`.
- Сессия агента привязывается к задаче и ветке; автономные отрезки
  помечаются — за выдачу автономного времени за активное время день
  помечается флагами и разбирается директором.
- Запрещено: менять правила расчета без ADR, отключать CI, отправлять
  код клиента во внешние модели без разрешения.

## 4. Догфудинг

«Партнер» разрабатывается сам через «Партнер»: работа над репозиторием
продукта учитывается в tenant #1 по его политике. Это обязательная
проверка правил на себе — расхождения фиксируются как задачи.
