## 1. Принципы разработки

1. **Golden-тесты первичны.** Правила расчета (T-01…T-12) закреплены тестами
   `tests/test_calc.py`; изменение правил = изменение тестов + документа
   + кода в одном PR, со ссылкой на ADR.
2. **DoD как шлюз.** Итерация не закрывается, пока не выполнены все
   критерии готовности; незакрытое переносится явно.
3. **Trunk-based.** Ветки `dev/<логин>/<тема>`, Conventional Commits, PR
   с ревью (см. development-process.md).
4. **Догфудинг.** Работа над самим репозиторием учитывается в tenant #1 —
   продукт постоянно проверяет сам себя.
5. **Прототип → сервер → поставка.** SQLite-прототип остается рабочим до
   конца M4; после этого SQLite сохраняется только как режим «embedded»
   для демо.

## 2. Стек и окружения

| Слой | Прототип (M0–M3, готов) | Целевое (M4+) |
|---|---|---|
| CLI | Python 3.11, Typer | без изменений |
| Хранение | SQLite (schema.sql) | PostgreSQL 16 + Alembic |
| Сервер | — | FastAPI + uvicorn |
| Сборки | pyproject.toml | Docker Compose (M8) |
| CI | GitHub Actions: pytest + policy_lint | + lint (ruff), интеграционные тесты |
| Часовой пояс | Europe/Moscow, закрытие дня 00:00 | без изменений (ADR-0017) |

Окружения: `local` (SQLite, демо-данные), `staging` (PostgreSQL, tenant #1),
`prod` (self-hosted у клиента).

### M6 · Дайджест и уведомления — ВЫПОЛНЕНО (2026-11-13)

Предусловие: M4 (M5 параллельно). Предусловие выполнено.

Выполнено: 6.1 дневной дайджест (`digest.py`) после закрытия дня — часы
по классам (пересборка из интервалов БД через golden-калькулятор), сумма ₽,
доля %, флаги, спорные интервалы; DoD «только числа, воспроизводимые из БД»
закреплен тестами (равенство с day_record; расхождение → `day_mismatch`);
6.2 месячный дайджест — оплачиваемые часы, вклад ₽, начисленные доли,
остаток пула (30% × 10 000 бп минус начисленные всем бп месяца), pending
(открытые споры + незакрытые дни); 6.3 каналы доставки (`notify.py`):
agent_chat (основной, встроен), email (fallback, SMTP), webhook
(мессенджеры, PARTNER_WEBHOOK_URL); очередь notifications с повтором
(attempts до 3, далее failed), ретраи при старте сервера и в планировщике
после закрытия дня; месячные дайджесты — джобой 1-го числа за предыдущий
месяц; 6.4 спор дня (`disputes.py`): разработчик помечает закрытый день
(опционально interval_id) через POST /v1/days/{date}/disputes или CLI
`partner dispute <date>`, директор решает в окне 3 дня
(PARTNER_DISPUTE_DAYS): approved → adjustment (append-only, ссылка на
day_record, эффективная сумма = amount + Σ корректировок в GET
/v1/days/{date} и дайджесте), rejected, авто-истечение expired
(`dispute_window_expired`). Миграция 0002_m6 (disputes, notifications).
Тексты дайджеста рендерятся детерминированно (render_day_digest /
render_month_digest) — формат к утверждению в D6 (документы 08-guides).

Тесты: tests/test_digest.py — 18 (всего в репо 66).

**DoD (выполнен):** дайджест дня содержит только числа, воспроизводимые
из БД (тест равенства с day_record + day_mismatch на порче записи); спор
и корректировка проходят полный цикл по документации (открытие → решение
в окне → adjustment → эффективная сумма, уведомления и аудит на каждом
шаге).

### M8 · Поставка и эксплуатация — ВЫПОЛНЕНО (2026-11-13)

Предусловие: M4, M5. Предусловие выполнено.

Выполнено:

1. **8.1 Docker Compose.** `deploy/`: docker-compose.yml — PostgreSQL 16
   (не публикуется наружу), разовый сервис `migrate` (alembic upgrade
   head, сервер стартует только после успешной миграции), `server`
   (healthcheck /healthz, планировщик закрытия дня PARTNER_SCHEDULER=1),
   `dayclose` (tools-профиль, разовая идемпотентная джоба
   `python -m partner_server.dayclose_cli [--date D]`), `backup`
   (ежедневный дамп). Секреты — только через .env (deploy/.env.example);
   Dockerfile в deploy/ (python:3.12-slim, postgresql-client).
2. **8.2 Обновления.** `deploy/scripts/upgrade.sh <тег>`: бэкап →
   alembic upgrade → перезапуск → ожидание /healthz; при неудаче —
   прерывание ДО перезапуска. `rollback.sh <тег> [дамп]`: откат образа,
   восстановление БД — только явно. Инвариант: закрытые дни неизменны
   между версиями (V-02/V-04); миграция 0004_m8 (closed_at) — идемпотентна,
   полный цикл upgrade→downgrade→upgrade проверен.
3. **8.3 Бэкапы.** `deploy/scripts/backup.sh`: ежедневный pg_dump -Fc в
   `PARTNER_BACKUP_AT`, проверка каждого дампа (gzip -t + pg_restore
   --list — битый дамп не считается бэкапом), retention
   PARTNER_BACKUP_KEEP_DAYS (14). Репетиция восстановления:
   `restore_check.sh` — восстановление во временную БД + сверка с боевой
   (версия схемы, ≥15 таблиц, количество и сумма day_records, sha256).
   Пересмотр ADR-0013 зафиксирован в **ADR-0020** (офсайт-копия
   обязательна).
4. **8.4 Мониторинг.** `GET /v1/metrics` (Prometheus text, без токена —
   только агрегаты, без персональных данных): heartbeats_total/last_hour,
   intervals, days_closed, **day_close_delay_seconds** (closed_at − 00:00
   след. дня, новая колонка closed_at в day_records), **days_open_overdue**
   (незакрытые дни старше грейса), digest_pending/failed, disputes_open.
   Алерт-правила и чек-лист дежурного — runbook §3, §6. Подпись устройств
   осталась в M9 (threat-model §4).
5. **8.5 Runbook.** `docs/07-ops/runbook.md` 1.0: точки здоровья, пороги
   алертов, типовые сбои (heartbeats, закрытие дня, доставка, спор,
   падение сервера, потеря данных с RPO/RTO, утечка токена), процедуры
   (репетиция восстановления, откат, ручное закрытие месяца);
   installation.md 1.1 (approved).

Тесты: tests/test_ops.py — 9 (всего в репо 90).

**DoD (выполнен):** установка по installation.md сводится к compose up с
заполненным .env (час по чек-листу без программиста); восстановление из
бэкапа отрепетировано скриптом restore_check.sh (логика покрыта
миграционным циклом alembic и сверкой day_records); закрытие дня
отслеживается метрикой day_close_delay_seconds с алертом > 900 с.
Живой PG-прогон compose — при первой установке у пилотного клиента
(критерий перенесен в M9.4).

## 5. Риски и меры

| Риск | Вероятность | Мера |
|---|---|---|
| Расхождение чисел сервера и прототипа | средняя | единый golden-набор T-01…T-12 гоняется в CI против обоих контуров |
| Часовой пояс клиента ≠ Europe/Moscow | средняя | tz — переменная политики с 00:00 Europe/Moscow как дефолтом; тесты на DST не требуются (в MSK нет перевода часов) |
| Фрод автономного времени | средняя | капы + флаги M5; спор дня M6 |
