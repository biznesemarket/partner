## 2. Атаки на время (новый класс после пивота) — реализация M5

| # | Атака | Детект (реализация) | Мера | Статус |
|---|---|---|---|---|
| T-1 | Агент запущен на ночь, человек спит | флаг night_autonomous_spike: автономные секунды в окне 22–24 ∪ 00–06 > 6 ч (night_spike_hours в политике) | k_autonomous 0,2 и кап 2,0 оплач. ч → ночь ≤ 1 000 ₽ (T-02/T-12) | ★ детект + тест |
| T-2 | Синтетический ввод (макросы, автокликеры) | флаг synthetic_input: ≥4 подряд интервалов одного класса длительностью ±5 с (SYNTHETIC_MIN_RUN) | день помечается, директор решает | ★ детект + тест |
| T-3 | Replay событий | повтор event_id → duplicate + инцидент incident.replay в аудите; повтор seq → 422 duplicate_seq + инцидент | начисление дня не меняется (интервал не дублируется) | ★ детект + тест |
| T-4 | Часы клиента сдвинуты | флаг clock_skew: конец интервала позже приема > max_clock_skew_sec (деф. 120 с); серверное время авторитетно | флаг | ★ детект + тест |
| T-5 | Много «параллельных» сессий | union интервалов (R3) в golden-калькуляторе | двойной оплаты не бывает | ★ тест T-04 |
| T-6 | Работа без привязки к задаче | флаг no_task_link: сессия без task_ref → интервалы в idle | не оплачивается | ★ тест M4 |
| T-7 | «Работа руками» без агента с полным тарифом | manual_only_policy: track_only (флаг manual_track_only) | учитывается, 0 ₽ (T-10) | ★ тест M4 |
| T-8 | no_output: часы есть, результата нет | флаг idle_no_signal: супервизия с signals {input_events:0, focus:0} → простой; флаг late_rejected: прием позже grace_hours (24 ч) | сигнал директору, спор через окно | ★ детект + тесты |

Опоздавшие события: в грейсе 24 ч — оплачиваются (T-08), за грейсом —
late_rejected, 0 ₽ до решения директора (T-09). Оба пути покрыты тестами.

## 3. Атаки на реестр и начисления

| # | Атака | Мера |
|---|---|---|
| R-1 | Подмена дневной записи | записи append-only; правка только компенсирующей записью с обоснованием |
| R-2 | Заднее число версии ставки | V-04 в policy_lint + проверка в БД |
| R-3 | Манипуляция снапшотом | SHA-256 входных записей + git-якорь; спорное — только через окно спора |
| R-4 | Обход капа изменением политики | политика версионируется; изменение действует с даты, не ретроактивно |
| R-5 | Сговор «отката» между участниками | вне технического охвата; снижается прозрачностью explain и правом директора |

## 4. Изоляция и периметр — реализация M5

- Тенантная изоляция: deny by default — `ensure_same_tenant` на всех
  чтениях дня/статуса и на создании сессии; кросс-тенантный запрос → 403
  cross_tenant_denied + инцидент в аудите. Покрыто тестами (чтение и
  создание сессии).
- Аутентификация: Bearer-токен при заданном PARTNER_API_TOKEN (M5.1).
  v1.2: `PARTNER_TENANT_TOKENS` привязывает токен к tenant; запросы к
  чужому проекту/участнику, а также списки статусов, споров, уведомлений,
  аудита и снапшотов фильтруются по tenant/project (issue #4).
  Подпись устройства (device_id + signature
  HMAC-SHA256, таблица devices, миграция 0005_m9) — реализована в M9:
  unsigned heartbeat-батчи при PARTNER_REQUIRE_DEVICE_SIGN=1
  отбрасываться там же. До M8 канал между agent-kit и сервером считается
  внутренним (VPN/loopback).
- Аудит (M5.4): append-only журнал audit_logs — кто, когда, старое/новое
  значение; инциденты (replay, duplicate_seq, cross_tenant_denied,
  rate_backdated) пишутся тем же механизмом; просмотр — GET /v1/audit.
- Не храним содержимое файлов, переписку, скриншоты — только метаданные
  активности (time-accounting §14).
- Дайджест и CLI не содержат данных других участников; директор видит
  сводку без содержимого работы.

## 6. Остаточные риски (приняты)

| Риск | Обоснование принятия |
|---|---|
| Человек «эмулирует» работу руками по вечерам | экономически невыгодно: автономный/пассивный класс не оплачивается, активный требует сигналов |
| Юридические споры о доле | закрывается юридическим модулем и снапшотами, не кодом |
| Компрометация устройства разработчика | подпись устройства помогает частично; полный контроль — задача нулевого доверия, вне MVP |

## 7. Пересмотр

Модель пересматривается при первом внешнем клиенте и после I5
(реализация детекторов аномалий в сервере).
